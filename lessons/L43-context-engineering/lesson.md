# L43 上下文工程：结构化笔记与即时检索

"Prompt engineering" 已经让位于 **context engineering**（Anthropic《Effective Context Engineering
for AI Agents》, 2025-09）：上下文不是无限速查表，而是**有限且会退化的资源**——Chroma 的
context rot 实验表明，即便新增内容与任务相关，输入越长性能仍会下降（位置敏感、一致性变差）。

四种应对技术，本实验室各有对应：

| 技术 | 一句话机制 | 对应课程 |
|---|---|---|
| 压缩 compaction | 近满时摘要重启新上下文 | L15（tool_result_head） |
| **结构化笔记** | 长任务中把关键信息持久化到文件/记忆 | **本课（remember）** |
| 子代理上下文隔离 | 子任务各自开窗口，只回传结果 | L31/L44 |
| **即时检索** | 只留轻量引用，用到才取细节 | **本课（search_documents）/ L11** |

本课同时开启 compaction（对照 L15），让你在一次运行里看到两种策略叠加。

## 观察要点

- **Prompt 页签**：逐次查看模型实际看到的消息——检索结果是否"即时"进入、旧工具结果是否被压缩为首段+指针。
- **信息流**：remember 写入与 search_documents 检索交替出现的节奏即"笔记→按需取回"模式。
- **运行页签**：输入 token 的增长曲线在笔记+检索模式下应明显低于"全量塞入"（可到历史页对比早期课程同类任务）。
- 图上「上下文编译」节点的计数即编译次数；每次编译的选入/排除原因都可点开（第四层证据）。

## 思考题

1. 结构化笔记与即时检索各自把什么成本从"上下文内"挪到了"上下文外"？代价是什么？
2. 子代理隔离（L44 将实践）与即时检索都控制窗口内容——它们解决的是同一个问题吗？
3. 如果任务中途换了检索关键词导致两次结果矛盾，笔记里应该存什么？（提示：存证据引用而非结论）
